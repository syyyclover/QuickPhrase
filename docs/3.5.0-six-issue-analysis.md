## 3. 逐项分析

### 问题 1　多选自主补充后鼠标指针消失　→ 已修复

**调用链**（`src/ui/main_popup.c`）：

1. 用户点弹层里的「（自主补充）」行 → `popup_toggle()`（`main_popup.c:214`）判定是自主补充项且尚未勾选 → 调 `ui_choice_multi()`；
2. `ui_choice_multi()`（`main_choices.c:63`）先 `memcpy` 一份勾选掩码，再 `popup_close()`（`main_choices.c:81`）——**释放鼠标捕获并销毁弹层**；
3. 进模态输入框 `dlg_input()`（`main_choices.c:82`），此时光标由输入框的类光标接管；
4. 输入框关闭后 `popup_open(index, anchor)`（`main_choices.c:90`）重建弹层，末尾 `SetCapture(g_popup)`（`main_popup.c:549`）。

**根因**：`SetCapture` 之后，系统不再把 `WM_SETCURSOR` 发给任何窗口 —— 光标形状只能由捕获方自己摆。而：

- `popup_open` 在 `SetCapture` 之后**没有**摆光标；
- `popup_proc`（`main_popup.c:352`）**完全没有** `WM_SETCURSOR` 分支，于是交给 `DefWindowProcW`。弹层的父窗口是主窗口，`DefWindowProc` 把这条消息转给主窗口，主窗口按「分隔条命中」的逻辑回一个 `IDC_SIZEWE`/`IDC_SIZENS`（`main_window.c:301-317`）—— 弹层压在分隔条那一列上时光标就变成缩放箭头。

对照证据：同一份代码里**锚点 Edit 是显式摆光标的**（`main_host.c` 的 `multi_edit_proc`，`SetCursor(IDC_ARROW); return 1;`）。也就是说「捕获/无激活这一族窗口必须自己摆光标」这条约定已经存在，只是弹层漏了。

**修复（已应用）**：

```c
/* src/ui/main_popup.c:362 — popup_proc */
    case WM_SETCURSOR:
        SetCursor(LoadCursorW(NULL, IDC_ARROW));
        return TRUE;

/* src/ui/main_popup.c:549 — popup_open，紧跟 SetCapture(g_popup) 之后 */
    SetCapture(g_popup);
    SetCursor(LoadCursorW(NULL, IDC_ARROW));
```

**回归用例**：`tests/popup_cursor.py`（已加入 Makefile 的 `PY_TESTS`）。改前 FAIL 2 项、改后 PASS —— 反向验证已做（用例里先 `re.sub` 剥注释，避免修复说明里的 `WM_SETCURSOR` 字样把用例喂绿）。

**待验证**：原生 Windows 上复现原路径（多选 → 勾「自主补充」→ 输入 → 确定），确认指针不再消失、也不再在弹层上变成缩放箭头。

### 问题 5　填写框瞬间变黑　→ 宿主窗口与主窗口都已修复

**根因**：`CLS_HOST`（填写区宿主）注册时 `hbrBackground = NULL`（`main_window.c:690-692`），整片背景只由它自己的 `WM_PAINT`（`qp_paint_background`）画。而系统在「带 ERASE 标志地失效」时会**先**发一条 `WM_ERASEBKGND` —— 从任务栏还原、放大缩小、拉边框都走这条路。原来的处理是：

```c
case WM_ERASEBKGND: return 1;   /* 只声称「已经擦过了」，一个像素都没画 */
```

新露出来的那圈底没人画 → 先呈现上一帧的残影或黑，等 `WM_PAINT` 到了才补上，肉眼就是「填写框瞬间变黑一帧」。这也解释了为什么只在还原/缩放这类**整窗重绘**场景出现，平时打字不出现。

**修复 1（宿主窗口，已应用）**：

```c
/* src/ui/main_host.c:76 */
case WM_ERASEBKGND: qp_draw_background(hwnd,(HDC)wp); return 1;
```

`qp_draw_background`（`text_paint.c`）就是 `GetClientRect + FillRect(dc, g_brushBk)`，也正是 `qp_paint_background` 内部复用的那一句。所以擦除趟与绘制趟画出来的**是同一份像素**（宿主窗口自己没有分隔条，不存在「先擦掉线再画上线」的问题）。代价是每次擦除多一次 `FillRect`。

**修复 2（主窗口，本轮按原方案 A 一并改掉）**：

```c
/* src/ui/main_window.c:616 */
case WM_ERASEBKGND: {
    RECT rc;
    int kind = GetClipBox((HDC)wp, &rc);
    if (kind == NULLREGION) return 1;          /* 没有要擦的地方 */
    if (kind == ERROR) GetClientRect(hwnd, &rc);
    main_draw_client(hwnd, (HDC)wp, &rc);
    return 1;
}
```

`main_draw_client` 是**唯一的客户区合成函数**（`FillRect(dc,&clip,g_brushBk)` + 两条分隔条 + `BitBlt` 整块贴上），`WM_PAINT` 与 `WM_PRINTCLIENT` 都走它。擦除趟与绘制趟像素完全相同 → 既不会黑一帧，也不会像「只涂背景不画分隔条」那样让分隔条先消失一帧（拖动时抽搐）。子控件自带 `WS_CLIPCHILDREN`，不受影响。同时更新了 `main_draw_client` 的过时注释（原文写「现在 WM_ERASEBKGND 什么都不做」）。

**回归用例**：`tests/host_erase_repaint.py`（宿主，改前 FAIL / 改后 PASS）、`tests/window_erase_repaint.py`（主窗口，把 `main_draw_client(...)` 三行换回 `return 1;` 后 FAIL 1 项，还原后 PASS）。两个都已挂 `PY_TESTS`。

**待验证**：原生 Windows 上连续最大化/还原/最小化、从任务栏恢复、拉边框，确认黑闪消失且拖动不抽搐。本机无法测帧，用例只能证明写法同源。

### 问题 2　偶发闪退（连后台进程也退出）

「连后台进程也退出」说明是**整个进程死掉**（托盘图标一起没了），不是某个窗口崩 —— 指向未捕获异常 / 堆损坏 / `abort()`，而不是普通的 Win32 消息错误。静态审查**无法定论**，需要转储。嫌疑路径按可能性排：

1. **借用表句柄**（有历史记录）。`qp_table_get()` 返回的是缓存里的指针，缓存只有 `QP_TABLE_CACHE_MAX = 4` 个槽，满了会回收 0 号并 `table_free`。数据表窗口列清单时会挨个 `qp_table_probe`，一 churn 就悬垂 —— **已经真的崩过一次**（查表匹配点「添加一项」直接闪退）。约定是「每次要用之前重新取一次」，只要有一处把返回值存进结构体用一整场就会复发。
2. **通知重入**（有历史记录）。ListView 的 `DeleteAllItems` / `InsertItem` / `SetItemState`、ComboBox 的 `CB_ADDSTRING` / `CB_RESETCONTENT` 都会**同步**给父窗口发通知。灌值期间没闸住 `loading`、或者闸门没恢复成 `was`（写成 0 会抹掉外层的闸），通知处理器就会当成用户操作跑一遍，进而重入 `commit`/重建列表。
3. **模板整体替换 + 借用 Segment 指针**。`eval_create` 让 `ctx->fields[i].seg` 借用模板的 `Segment`；`ui_edit_current` 的次序（先 `ui_select_template(NULL)` 再 `tmpl_list_replace`）**看起来是封住的**，`sess_prune()` 也只按「模板 id 还在不在」判断 session 死活。但这条链环数多、跨了 UI 与引擎两层，属于「必须用 ASan 跑一遍才能排除」的类型。

**已应用的取证手段（新增代码，不是修复）**：

`src/platform/crash.c` / `crash.h` + `src/platform/main.c` 的两处接线：

- `qp_crash_init()` 装 `SetUnhandledExceptionFilter`（SEH）+ `signal(SIGABRT)`（`abort()` / CRT 堆损坏 / `__stack_chk_fail`）；
- 日志写到数据目录的 `crash.log`，每行：
  `[YYYY-MM-DD HH:MM:SS] tag=SEH|SIGABRT|signal pid= tid= code=0x addr=0x module=X+0x lastmsg=0x hwnd=0x wp=0x`；
- `qp_crash_note_message()` 在消息循环里记住**最后一条消息**（`hwnd`/`message`/`wParam`）—— 崩溃时能看出「死在哪个窗口的哪条消息」；
- `try_dump()` 在运行时 `LoadLibrary("dbghelp.dll")` 调 `MiniDumpWriteDump` 写 `.dmp`（避免静态导入）；
- 落盘用 `CreateFileW(FILE_APPEND_DATA)` + `WriteFile`，**不用 `fprintf`** —— 避免把窄字符 stdio 拖进来；日志行用自写的 `put_str/put_dec/put_hex` 拼 ASCII。

**体积代价（待你拍板）**：三静态缓冲那一版实测 `456704 B`（+6656 B，app 余量 8704 → **2048 B**）。随后改成「只留一个静态缓冲、其余用栈上缓冲」的结构调整版，静态推算约 `+4576 B`（余量约 2528 B），但**编译机掉线，未实测**。

**其余取证路径（未跑）**：

1. `make sanitize`（ASan + UBSan，宿主侧跑 `src/core`）—— 纯算法层的堆/越界问题能直接抓到。注意共享固定临时夹具的测试套件不要同时跑。
2. `tests/allocator_instrumentation` 已经在了，配合崩溃记录器一起用。
3. 复现 1、2 两条已记录路径的周边操作（数据表窗口连续加/删项、查表匹配里反复「添加一项」、模板编辑保存后立刻改选项），每步之间看是否报 `__stack_chk_fail` / CRT invalid parameter。

**不建议**：为了省体积去掉 `.pdata`/`.xdata`（见问题 3）。那会破坏栈展开 —— 在一个还没查清的崩溃上做这件事，只会让下次崩溃更难查。

### 问题 3　体积　→ 按你的意见不动

实测（基线，未含崩溃记录器）：

| 产物 | 实测 | 门槛（`tests/size_budget.py`） | 余量 |
|---|---|---|---|
| `QuickPhrase.exe` | 450048 B | 458752 B | **8704 B（1.9%）** |
| `QuickPhrase-3.5.0-setup.exe` | 586752 B | 589824 B | **3072 B（0.5%）** |

段构成：

```
QuickPhrase.exe   .text 323072(71%)  .rsrc 53248(11%)  .rdata 32256(7%)
                  .xdata 10752  .pdata 10240  .idata 10240  .data 7680  其余 <1KB
setup.exe         .rsrc 559104(95%)  ← 内嵌的 app + uninstaller，未压缩
                  .text 13824(2%)  其余 <5KB
```

**已拿到的优化**（Makefile 里都在）：`-ffunction-sections -fdata-sections` + `-Wl,--gc-sections` + `-s`、核心 `-O2` / UI `-Os`。**已试过并否决**：全 LTO = 372224 B、全 Os = 401920 B、mixed = 439296 B —— 正则在 LTO/Os 下约退化 2.94/3.21 倍、查表退化约 15.8%/17.2%（`docs/3.5.0-hardening-results.md`）。否决合理，不翻案。

**你已决定不动**，方案存档备用：

1. **压缩 setup 内嵌载荷** —— setup 的 95% 就是原封不动塞进去的 `app` + `uninstaller`。压完可从 ~587 KB 降到 200 KB 量级，且**不碰主程序一行代码**（完全绕开 LTO/Os 的否决理由）。解压器不必引第三方库：`ntdll!RtlDecompressBuffer`（LZNT1）系统自带，`GetProcAddress` 动态取；或塞 miniz/uzlib 级小解压器（约 +2–4 KB `.text`）。压缩步骤用 Python（已是构建依赖）。
2. **`.rsrc` 的九尺寸 ICO（53248 B，占 app 11.8%）** —— 砍到实际会用到的 4–5 档约省 25–30 KB，但这是**产品取舍**（项目此前明确决定保留全部九尺寸），要你重新拍板。
3. **`.pdata` + `.xdata`（20992 B）** 可砍但**破坏栈展开**，在问题 2 查清前**不要动**。

#### 问题 3 的补充：崩溃记录器引入了 setup 体积回归（本轮实测）

崩溃记录器（你要求添加）让 `build/QuickPhrase.exe` 从 450048 → **456192 B**（+6144，仍在 app 门槛内，余 2560）。
但 setup 的 `.rsrc`（565248 B）里内嵌的是**未压缩的 app**，于是 setup 从 586752 → **592896 B**，**超出门槛 589824 B 共 3072 B，`make -B setup` 直接失败**（`size_budget.py` 在构建末尾校验，返回非零）。

三条路：

| 方案 | 效果 | 代价 |
|---|---|---|
| **① 上调 setup 门槛**（`tests/size_budget.py`：589824 → 614400） | 立即恢复可构建 | 改的是预算不是代码；setup 仍是 579 KB 的庞然大物 |
| **② 压缩 setup 内嵌载荷**（即上面第 1 条方案） | setup → 200 KB 量级，**余量从 −3072 变成 +380 KB 左右** | 改 Makefile（加 Python 压缩步骤）+ installer 加解压器（`RtlDecompressBuffer` / miniz），是独立一轮的活 |
| ③ 精简崩溃记录器 | 不够 —— 去掉 `.dmp` 转储也省不到 3072 B | 且削弱问题 2 的取证能力 |

**app 本身没有超预算**（456192 ≤ 458752）；破线的是 setup。**已按 ① 处理**：`SETUP_MAX` 589824 → 614400（600 KB），`make -B setup` 实测恢复通过。②（压缩内嵌载荷 → 200 KB 量级）是根治方案，留待需要时做。

### 问题 6　编辑模板多选选项并保存后，选项更新不及时（多个地方都有）

**先说结论**：这条最可能**不是缓存**，而是**交付层**问题。项目自己的记录已经写明：

> 不能断定未看到成效是缓存或构建造成。已查明两个错版风险：整理之前的根目录程序比独立目录程序旧；全局单实例锁可能使新 EXE 退出并唤起旧进程。
> —— `docs/delivery-status.md:7`、`docs/windows-build.md:3`

这条与「**多个地方**都有」的观察高度吻合：如果跑的是旧进程，那么填写界面的单选下拉、多选弹层、预览、编辑器看到的**全都是旧模板**，而不是某一处没刷新。

#### 本轮实测：确实存在一份 **3.3.0** 的旧安装，而且和新构建**共用同一把锁、同一个数据目录**

把本机磁盘扫了一遍（`/c /d /e /f`，深度 6），QuickPhrase 可执行体只有四处：

| 路径 | 版本 | 大小 | 时间 | SHA256 前 16 位 |
|---|---|---|---|---|
| `D:\soft\documents\QuickPhrase\build\QuickPhrase.exe` | 3.5.0 | 456192 | 2026-10-12 16:17 | `6b8f00fbb8831f99` |
| `D:\soft\documents\QuickPhrase\dist\QuickPhrase.exe` | 3.5.0 | 456192 | 2026-10-12 15:13 | `972fc7d209d4d9b1`（= `dist/SHA256SUMS`） |
| **`D:\soft\documents\新建文件夹\QuickPhrase\QuickPhrase.exe`** | **3.3.0** | **390144** | **2026-09-11** | `3464f04d3c3b8bd8` |
| `D:\$RECYCLE.BIN\…\$R64LTB6\QuickPhrase.exe` | 旧 | 3700224 | 2026-08-14 | `2d7dee84183c30fb` |

那份 3.3.0 是**装出来的**（同目录有 `uninstall.exe`，旁边还有 `QuickPhrase-模板.json`、`示例.*`）。逐字节比对确认它就是 3.3.0，不是 3.5.0 的改名。

**更关键的是它和 3.5.0 完全共享运行环境**（从 `snapshots/3.3.0/dist/QuickPhrase.exe` 里直接抽字符串比对）：

| 共享项 | 值 |
|---|---|
| 单实例互斥体 | `QuickPhrase.SingleInstance.Mutex` —— 两版**同名** |
| 数据目录 | `%ls\QuickPhrase`（即 `%APPDATA%\QuickPhrase`）—— 两版**同目录** |
| 唤起消息 | `QuickPhrase.ShowMainWindow` / `QuickPhrase.RequestExit` |

于是 `src/platform/main.c:455` 这段的行为就是**静默换人**：

```c
s_mutex = CreateMutexW(NULL, FALSE, QP_MUTEX_NAME);
if (s_mutex && GetLastError() == ERROR_ALREADY_EXISTS) {
    if (g_msgShowWindow) PostMessageW(HWND_BROADCAST, g_msgShowWindow, 0, 0);
    CloseHandle(s_mutex);
    return 0;          /* 新进程直接退出，没有提示、没有日志 */
}
```

**只要你从托盘里没退出 3.3.0，双击 3.5.0 的 EXE 就会：新进程立刻退出（退出码 0）→ 广播唤起 → 弹出的是 3.3.0 的窗口。** 界面看起来「启动了」，实际跑的是九月的代码，而两者数据目录相同，所以你甚至看不出数据是共享的。这就是「选项更新不及时、多个地方都有」的最直接机制。

**顺带查清的三件事**：

- **不是数据分叉**：`%APPDATA%\QuickPhrase\data.json`（57766 B）里是真实数据（分组「管控 / 每日巡检 / 关单 / 填表」，模板「日间管控」等，`createdAt 2026-08-18`、`updatedAt 2026-10-09`），**没有任何测试夹具痕迹**（`测试日期`/`补充选项测试`/`Other` 计数全为 0）。两个版本读的是同一份。
- **没有自启动路径**：扫了桌面、用户级 + 全机级「开始菜单」（共 177 个 `.lnk`）、Quick Launch、两个 Startup 文件夹 —— **没有任何快捷方式指向 QuickPhrase**（安装器建的那个已不在）。所以 3.3.0 只会被「直接双击那个 EXE」启动。`settings.json` 里 `autostart: false`，注册表 Run 项因 `reg.exe` 被安全策略拉黑**未能核验**，需要你自己看一眼。
- **构建不可复现（新发现，小事但会咬人）**：`build/QuickPhrase.exe` 与 `dist/QuickPhrase.exe` 源码完全相同、大小都是 456192，但**逐字节比有 4 个字节不同** —— 全在 PE 头的 `TimeDateStamp` 里（`ld` 每次链接写入当前时间）。后果：`make -B app` 之后 `build/` 与 `dist/` 不再逐字节相同，`docs/delivery-status.md` 要求的「程序与 `build/QuickPhrase.exe` 逐字节相同」**在任何一次重建后都会假性失败**，`dist/SHA256SUMS` 也只能对应「当时那一份」。一行可修：链接时加 `-Wl,--no-insert-timestamp`（把该字段写 0），构建即变成可复现、哈希可校验。**未改，等你点头**（会改变产物字节，需要重出一次 `dist/`）。

#### 所以判别步骤简化成一句话

**启动后核对正在运行的那个进程的路径**（任务管理器 → 详细信息 → 右键列头 → 勾「命令行」，或）：

```powershell
Get-Process QuickPhrase -ErrorAction SilentlyContinue | Select-Object Id, Path, StartTime
Get-FileHash (Get-Process QuickPhrase).Path -Algorithm SHA256
```

- 路径应当是 `D:\soft\documents\QuickPhrase\build\QuickPhrase.exe` 或 `dist\QuickPhrase.exe`；
- 哈希应当是 `6b8f00fb…`（build）或 `972fc7d2…`（dist）。**对不上就是在跑旧版。**

**建议（需要你点头，我不动你的文件）**：

1. 把 `D:\soft\documents\新建文件夹\QuickPhrase\` 整个改名或移走（例如加后缀 `.3.3.0-old`），让它不可能被误双击 —— 这是**一次性根治**；
2. 可选加固：让「第二个实例」在发现**版本不同**时弹一句提示（现在是静默退出）。实现方式：`FindWindowW(L"QuickPhraseMain")` → `GetWindowThreadProcessId` → `QueryFullProcessImageNameW` 拿路径 → `GetFileVersionInfoW` 读它的版本 → 与本进程比对。旧版不发布任何信息也能查出来，代价是多链一个 `version.dll`。**这属于新增可见 UI，等你同意再动。**

**静态审查的结论**：正常路径其实是通的，我逐环核过：

- `ui_edit_current()`（`main_tree.c:192`）：`sess_capture_current()` → `tmpl_clone` → 模态编辑器 → 成功后 `ui_select_template(NULL)`（**先切断引用**）→ `tmpl_list_replace()`（`model.c:833`，按 id 匹配并保留链表位置，`tmpl_free` 旧对象）→ `app_save_data()` → `ui_rebuild_tree(id)`；
- `ui_rebuild_tree()`（`main_tree.c:50`）→ `TreeView_SelectItem(selItem)` → `TVN_SELCHANGEDW`（`main_window.c:558`）→ `ui_select_template(新对象)` → `ui_build_fields()` 用**新** `seg->options` **全量重建** ComboBox；
- 选项本身是**直接写在活片段上**的（`ed_opt_add/edit/del/move` 操作 `s->options`，IDOK 里 `ed_commit_props` + `ed_commit_table`），不存在「暂存在临时表、忘了 commit」的漏写；
- `ui_select_template` 的 `if (t == g_curTmpl && g_ctx) return 1;` 早退（`main_fields.c:381`）在这条路径上不会命中，因为前一步刚把 `g_curTmpl` 置空。

**结论收窄**：既然选项**列表**每次都会重建，那么「用户看到的是列表本身没更新」几乎只能归到交付层（旧 EXE / 旧进程）—— 这也正好解释「多个地方都有」。**若**在确认跑的是新 EXE 后仍能复现，才轮到下面这条**真实的代码级缺口**：

`sess_activate()`（`main_sessions.c:201`）在切换模板时，按**片段 id** 把旧值搬到新上下文：

```c
if (index >= 0 && f->user_touched) eval_set_user_value(next, index, f->user_value);
...
qp_strlcpy(to->custom_value, f->custom_value, QP_VALUE_MAX);
qp_strlcpy(to->choice_base, f->choice_base, QP_VALUE_MAX);
```

**搬完不校验**。于是「把某个选项改名或删掉」之后：

- 单选：`ui_sync_controls()` 用 `CB_FINDSTRINGEXACT` 在**新**选项表里找旧值（`main_fields.c:159-162`），找不到就 `CB_ERR`，但控件里仍旧显示旧文字 → 下拉里没有这一项，框里却有；
- 多选：Edit 里是 `qp_choice_join` 拼出来的旧串，仍含已删除的选项；
- 预览：直接用这个值 → 输出里还带着已删掉的选项。

三处同时出现，是「多个地方」的另一种解释。**注**：`ui_sync_controls`（`main_fields.c:181-188`）对「值不在列表里」是**特意**临时加一项来显示的（只保留一个 `extraIndex`），所以这是**有意行为**，不是 bug —— 只是它让「模板已改、界面还留着旧值」看起来像没更新。

**修复方案（已按口径 A 实施）**：

- **口径 A（已采用）**：迁移后按新选项集**重算**一次 —— 值里已不存在的选项丢掉、仍存在的保留，自定义补充文字保留但重新计算勾选掩码。语义是「模板是权威，旧值向新选项对齐」。
- 口径 B（未采用）：只对**已被规则/默认值覆盖**的字段重算，`user_touched` 的手填值原样保留。语义是「用户输入是权威」。

**实现（本轮新增）**：

1. **core 层加投影函数** `qp_choice_realign()`（`src/core/choices.c`）。它把「已保存的旧值」投到 `seg` 当前的选项集上，填一个 `checked[]` 掩码并回传自主补充文字，返回值三态：
   - `>0` = 保留的项数 → 调用方用 `qp_choice_set()` 写回；
   - `0` = 旧值一项都对不上了 → 调用方清空该字段；
   - `-1` = **认不出**（多选按 `sep` 拆不开、且一段都没命中）→ 调用方**保持原值不动**。

   单选没有分隔符歧义（旧值要么等于某一项、要么是自主补充），对不上就是「这一项已被删/改名」→ 直接按口径 A 丢弃。
   多选用「拆出了几段」判定分隔符是否可信：**拆得开（≥2 段）才允许清空**；拆不开宁可留着旧值 —— 不拿用户手填的内容去赌一个猜错的分隔符。

2. **UI 层加执行者** `sess_reconcile_choices()`（`src/ui/main_sessions.c`），在 `sess_activate()` 的两条迁移分支之后、`qp_eval_run_checked()` 之前调用。只处理单选/多选、且只处理 `user_touched` 的字段（没填过的字段保持模板默认值）。

3. **回归用例**：`tests/test_choice.c` 扩展了行为断言（三项都在 / 删一项 / 全删 / 分隔符认不出 / 只填补充文字 / 选项删光 / 单选值被删），`tests/choice_realign.py` 是本机可跑的源码契约用例。改前 FAIL / 改后 PASS 已反向验证（含修正一处用例自身的假通过：函数开头还有一句防御性 `return -1`，全局搜会误判）。

**已知限制（诚实记录）**：`sess_activate` 走「跨会话」分支时拿不到**旧模板**（编辑保存的路径上旧模板对象已被 `tmpl_list_replace` 释放），所以对齐用的是**新模板**的分隔符。若用户**同时**改了模板分隔符和选项，旧串拆不开 → 返回 -1 → 保持原值（不丢数据，但也没对齐）。模板级分隔符很少改，且这条限制只会「少治」不会「治坏」。

**仍然要提醒**：这条代码级缺口只解释「某一处显示旧值」。若用户看到的是**列表本身没更新**（下拉里根本没有新选项），那是交付层，先做上面的判别步骤。
