# 3.5.0 深度审查：数据安全、绘制与体积

日期：2026-10-07。触发证据：`PixPin_2026-10-07_12-41-29.png`。截图同时出现跨越列表、属性区的旧边框和重复“默认值预览”文字，不能继续将其归类为单个 Static 标签的闪烁。

以下记录的是实施前的调查与方案阶段，源码行号和体积均为当时基线。2026-10-08 的实际修复、回归、候选包及未执行项见 [加固报告](3.5.0-hardening-results.md)。本审查不代表已发现软件的全部潜在问题，也不代表绘制假设已在真实 Windows 证实。

## 验证基线及盲区

`make -j4 test` 在当前代码通过（`build/deep-audit-baseline.log`），包含 10 个 C 程序和 16 个 Python 检查。真实业务夹具仍缺失。新增的定向探针却复现了数据完整性和查表错误，说明已有绿色测试不能证明这些路径安全。

核心探针使用唯一临时目录与自建 CSV，不接触用户数据；源码 `/tmp/qp-logic-audit.qDGuDv/probe.c`。主代理已复跑普通版本和 UBSan 版本。下次实施应将这些探针转为入库回归，逐点扫查失败而非只测试一个分配位置。

`tests/test_win32.c:154` 的原生拖动测试在每次缩放后主动强制整窗、全部子窗口即时重画，可能先消除产品本身的残影再检查；并未验证自然重绘结果。当前 Linux/Wine 沙箱不能执行 Windows 视觉验收，这个限制没有改变。

按“可能丢数据/填错记录优先”排序。前六项已执行探针；后三项为源码完整调用链确认，尚未执行真实 Windows 操作。

## 绘制：确定事实与未证实机制

已排除两个猜测：编辑器两个原生布局批次分别只包含同一父窗口的子控件，未违反 same-parent 约束；父窗口缓冲绘制的 viewport/blit 坐标一致，不能仅因其屏蔽 WM_ERASEBKGND 就判定错误。

当前最强假设是尺寸变化时保留的旧像素叠加后代窗口失效不足：

- 编辑器类只用 CS_DBLCLKS，没有调整尺寸变化时的客户区像素保留策略。
- `qp_defer` 对纯移动保留像素；外层提交后才执行属性区内层布局。
- `ed_layout` 显式清理只有父窗口的分隔条带，没有涵盖子控件/非客户区。父窗口 WS_CLIPCHILDREN 不能擦除已经落进子窗口的旧边框。
- 大多数兄弟控件没有 WS_CLIPSIBLINGS，布局中间态发生重叠时存在交叉绘制风险；尚缺实际消息/矩形轨迹证明。

Windows 客户区保留和重绘规则见 [WM_NCCALCSIZE](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-nccalcsize)、[SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos)。文档解释机制，但不能替代本项目在 Windows 的复现。

必需的新回归：先正常缩放/拖分隔条、泵送消息，不额外失效，抓取实际像素；同一几何下再强制完整重绘，抓取参考图，比较非光标/非动画区域。分别覆盖单改宽、单改高、缩小再放大、分隔条、属性滚动及主题切换。用诊断确定是否需改变父窗保留策略、提交后的损坏区域覆盖或兄弟裁剪，不能直接用“每帧整窗同步重画”遮蔽错误。

另外：编辑器最低客户区 880×690 逻辑像素，125% 下仅客户区高度已约 863px，超过 768px 屏幕；首次没有记忆尺寸时 `ed_restore_size` 直接返回。窗口居中也未按 owner 所在显示器工作区夹取。需要可在较小工作区使用的布局，而不是仅靠高 DPI 放大最小尺寸。

## 体积：测量而非猜测

从保留的 3.4 安装包提取内嵌程序，与当前 3.5 产物比较：

- 主程序文件增加 40,960 B，但 .text 原始段从 321,024 B 降至 312,832 B；不是主要代码段变大。
- 主程序 .rsrc 从 57,344 B 增至 102,912 B。`resource.rc:9–10` 把同一个 app.ico 嵌入两组；小图标 ID 没有运行时引用，九个图像负载成对重复。
- 安装包从 548,352 B 增至 626,688 B（+78,336 B）；安装器本身和卸载器的新图标也贡献增量。
- cJSON 当前导出 78 个函数；私有静态链接程序不需要该导出表。隐藏符号本次只节约 2,560 B，不能夸大成整块库代码被移除。
- 当前 --gc-sections 确实生效（对照节约 7,680 B）；函数/数据分段选项虽然放在链接变量里，一步 GCC 编译仍会使用，不能误判为失效。

唯一临时构建目录：`/tmp/quickphrase-size-audit.K06wuW`。没有修改生产构建或替换 dist。

## 性能与结构审查方向

- 编辑器每次预览都重新创建并销毁 EvalContext；输入通知触发全量规则求值。先测量事件/求值次数和耗时，再引入可复用工作缓冲、适度合并输入通知，复制时仍同步到最新值。
- 预览内容/标记未变也会重新构建显示模型、清选区、回顶。应区分内容变化、尺寸变化、字体变化和仅主题变化；重复结果不清用户阅读位置。
- 普通标签、属性背景和预览每次绘制申请位图/DC，失败路径不一致；预览缓冲创建失败直接验证掉绘制请求而不画内容。必须有正确的直接绘制降级，再评估按实例复用缓冲的价值和资源上限。
- 查表 FIRST/LAST 仍收集全部重复命中，多个输出重复查同一个键。可复用一次查询结果，索引记录首/末行，保留旧规则优先级和多命中顺序。
- 布局计算、滚动收敛、可见性状态、失效区域及模型提交目前散落在约 1,900 行编辑器文件中。建议按职责建立明确边界，不进行单纯换目录或整框架重写。

## 建议改造边界（待设计确认）

两种路径：

- 按每个症状保留现有分散的提交/绘制代码，逐项加校验：单项改动更小，但相同的所有权、回滚和失效策略仍需在多个入口维护，测试也容易只覆盖其中一个入口。
- 保留 Win32 和业务模型，集中“完整候选对象、提交/回滚、布局损坏区域”这三类职责：改动范围较大，需要分阶段回归，但可以用统一接口覆盖多个入口，后续性能与体积也有可重复基线。推荐这条路径，不引入新的 GUI 运行时。

推荐继续 C11＋原生 Win32，保留全部现有功能、JSON、规则优先级与快捷键，版本仍为 3.5.0。依次完成：

1. 数据安全：完整对象/失败事务、序列化逐点故障注入、规则所有权转移和取消语义。
2. 绘制正确性：自然绘制与参考重绘对照、统一布局提交/损坏区域/滚动收敛，工作区适配和真实 DPI 字体边界。
3. 查表与文本：精确完整键、合法空值、缓存一致性、UTF-16 和显式截断反馈。
4. 性能与减重：建立基准，避免无变化重算/重建，资源去重和编译选项对照，新增体积预算。

修复以失败回归为起点；完整 test、sanitize、setup 和资源检查不可删减。Windows 自然拖动、图标、实际业务模板及安装升级仍是独立发布门槛，不以模拟检查或强制重绘后的截图代替。不能保证“所有问题已找到”，但每一项确认缺陷都应有独立验证证据和状态。
