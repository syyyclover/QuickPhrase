# 下拉框原生高度与重复布局

用户的完整分控件日志 `resize-timing-29800.csv` 未丢记录。70 次布局中，分组、批量来源、变量类型、表格插入等 ComboBox 各出现 136 次 WM_SIZE。分组控件实际客户区始终为 225×28，布局仍要求逻辑行高 DPIX(24)，导致系统重新调整收起高度。即使宽度没变也反复摆位、擦除与绘制。

`qp_defer` 现在对 CBS_DROPDOWN/CBS_DROPDOWNLIST 保留已有的原生高度，继续应用位置和宽度。仅在请求与当前高度均为正且不同时识别类名/样式；CBS_SIMPLE 与零高度请求不变。下拉弹层高度仍由 `qp_combo_dropdown_fix` 直接 SetWindowPos 管理；创建时先设置字体，布局使用系统已经算出的收起高度。修改在共享队列，主界面等其他队列用户也适用。

`layout_damage.py` 新增稳定尺寸不提交、宽度变化保留原生高度、CBS_SIMPLE 显式高度回归。旧实现断言失败，修正后通过；既有分配/原生摆位失败与损伤覆盖回归保留。Linux 顺序完成 make test、默认 make sanitize（含泄漏检查）、make setup。两组业务夹具缺失及既有差分边界仍保留；日志在 `build/editor-combo-results/`。静态复核未发现重要问题；没有运行桌面自动化。

这些日志也显示片段列表 WM_PAINT 平均约 9.55ms、预览 WM_PAINT 约 6.36ms（含嵌套调用），说明重复 ComboBox 布局只是已确认的一项开销，不能据此宣称整体流畅度已达标。应由新版手工反馈和计时确认。

## 用户新版计时

`resize-timing-31020.csv` 无丢失记录，包含 30 次布局。分组与批量来源下拉框的 WM_SIZE 均降为 0，变量类型和表格插入下拉框各 15 次，已不再每次布局强制收起高度。布局均值 39.34ms、P95 67.29ms、最长 72.309ms，最终绘制均值仍为 26.51ms；外层几何提交均值 4.67ms。

旧诊断进程继续追加后为 130 次布局，均值 48.78ms、最终绘制 28.29ms、外层几何 10.55ms，两个固定尺寸下拉框各有 252 次 WM_SIZE。两次操作和窗口尺寸样本不同，不能据此声称严格的性能提升百分比；可确认无意义的固定尺寸 ComboBox 调整在新日志中消失，整体流畅度仍需用户反馈。
